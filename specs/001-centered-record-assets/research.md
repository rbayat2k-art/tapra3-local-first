# Research: پنجره‌های عملیاتی و دارایی‌های پرسنلی

## تصمیم ۱: پوسته مشترک برای پنجره‌های جزئیات

**Decision**: یک `RecordDialog` مشترک برای لایه، semantics و مدیریت focus ساخته شود و محتوای هفت drawer موجود بدون انتقال منطق دامنه درون آن قرار گیرد.

**Rationale**: هفت مصرف‌کننده واقعی ساختار یکسان دارند. تغییر صرف CSS مشکل focus، Escape و بازگشت focus را حل نمی‌کند؛ کپی‌کردن hook در هفت فایل نیز drift ایجاد می‌کند.

**Alternatives rejected**:
- فقط CSS: دسترس‌پذیری و focus ناقص می‌ماند.
- استفاده مستقیم از Modal محلی Personnel: export عمومی و قرارداد اثبات‌شده ندارد و refactor خانواده دیگر modalها را ناخواسته وارد scope می‌کند.

## تصمیم ۲: خطای عملیات به‌صورت alert بالاتر از modal

**Decision**: خطای سراسری `FoundationApp` در viewport و با z-index بالاتر از پنجره نمایش داده شود؛ validationهای محلی دست‌نخورده بمانند.

**Rationale**: همه drawerها از مسیر مشترک `execute/run` استفاده می‌کنند. این راه بدون تغییر امضای فرمان‌ها، خطا را هنگام بازبودن فرم قابل دیدن و announce می‌کند و state فرم را حفظ می‌کند.

**Alternative rejected**: تزریق خطای سرویس داخل تک‌تک هفت فرم، چون به تغییر گسترده قرارداد execute و تکرار state نیاز دارد.

## تصمیم ۳: بازاستفاده از نمای دارایی خودکاربر

**Decision**: `MyAssetsSection` یک حالت `personnel-profile` فقط‌خواندنی بگیرد و با همان state موجود در پرونده پرسنلی render شود.

**Rationale**: این جزء همین حالا دارایی جاری، انتقال باز، تاریخچه، رسید و گزارش مشکل را از stores فعال استخراج می‌کند. reuse از دو نمایش ناسازگار و داده تکراری جلوگیری می‌کند.

**Alternative rejected**: ساخت read model یا store جدید، چون داده لازم موجود است و قانون اساسی ایجاد persistence غیرضروری را منع می‌کند.

## تصمیم ۴: تعویض تخصصی دارایی خارج از scope

**Decision**: این مرحله فرمان «پس‌گرفتن و تحویل جایگزین در یک عملیات» اضافه نمی‌کند.

**Rationale**: runtime فعلی گزارش مشکل را به asset-maintenance می‌فرستد و عودت/تحویل را جداگانه با تأیید دوطرفه انجام می‌دهد. اتصال دارایی قدیمی و جدید، وضعیت نهایی و atomicity به تصمیم محصول و طراحی دامنه مستقل نیاز دارد.

## ریسک‌ها و کنترل‌ها

- **چاپ خزانه**: selectorهای فعلی `drawer-scrim` و `treasury-payment-drawer` حفظ و با تست چاپ کنترل می‌شوند.
- **موبایل**: در عرض کم، full-width bottom sheet و بدون overflow افقی حفظ می‌شود.
- **مجوزها**: در نمای پرونده هیچ دکمه OTP/گزارش/عودت ارائه نمی‌شود؛ عملیات در ماژول‌های معتبر باقی می‌ماند.
- **خطا**: alert سراسری متن، role و دکمه بستن دارد و فقط با رنگ ارتباط برقرار نمی‌کند.
