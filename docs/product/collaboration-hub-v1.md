# هاب همکاری شاهراه — قرارداد محصول V1

> **وضعیت سند:** `Implemented — verification pending` — دامنه، رابط کاربری، مهاجرت و آزمون‌های هاب پیاده‌سازی شده‌اند؛ برچسب نهایی `Verified` فقط پس از عبور آخرین Gate کامل و بازبینی مستقل ثبت می‌شود.
>
> **تاریخ:** ۲۰۲۶/۰۸/۲۷
>
> **مرجع معماری:** `ADR-016` در `docs/17-DECISIONS.md`

## ۱. هدف و مرز ادعا

هدف V1 ساخت یک فضای همکاری پروژه‌محور در شاهراه است تا کاربر بتواند پروژه‌های عضو خود، کارهای امروز و عقب‌افتاده، وظایف فردی، گفت‌وگو، نامه‌ها و اسناد مرتبط را از یک نقطه پیدا و پیگیری کند.

این نسخه روی `LocalFoundationService`، `StorageAdapter` و IndexedDB همان مرورگر اجرا می‌شود. عبارت «هاب همکاری» در V1 به معنی پیام بلادرنگ، حضور آنلاین، همگام‌سازی بین دستگاه‌ها، Push، فایل مرکزی، قفل توزیع‌شده، امنیت تولیدی یا پشتیبان‌گیری سروری نیست. UI باید این محدودیت را صادقانه نمایش دهد و هیچ سندی وضعیت محلی را «آماده بهره‌برداری سازمانی» معرفی نکند.

## ۲. بازیگران

| بازیگر | نیاز اصلی | اختیار پایه |
|---|---|---|
| عضو پروژه | مشاهده پروژه و منابع مجاز، انجام وظیفه خود | فقط پروژه‌هایی که عضویت صریح دارد |
| مسئول وظیفه | شروع، ثبت چک‌لیست، اعلام مانع و تکمیل وظیفه خود | عضویت پروژه + مجوز Task + انتساب همان Task |
| مالک پروژه | ویرایش پروژه، مدیریت اعضا و پیگیری همه وظایف پروژه | عضویت اجباری + مجوز مدیریت پروژه |
| مدیر پروژه مجاز | مدیریت عملیاتی پروژه بدون تغییر مالکیت مگر با command صریح | عضویت پروژه + `task.project.manage` |
| سازنده نامه/گفت‌وگو | استفاده از قابلیت تخصصی موجود از داخل هاب | همه مجوزها و قواعد فعلی Letter/Chat |
| ادمین/QA | مدیریت سامانه یا مشاهده آزمایشی طبق نقش فعلی | هیچ bypass ضمنی برای عضویت، Chat یا Letter ندارد |

واحد سازمانی، سمت و شعبه فقط زمینه سازمانی هستند؛ هیچ‌کدام به‌تنهایی عضویت پروژه ایجاد نمی‌کنند. نام نمایشی هرگز کلید هویت نیست و همه ارتباط‌ها با شناسه پایدار کاربر/پرسنل/واحد ذخیره می‌شوند.

## ۳. آنچه اکنون واقعاً وجود دارد

### ۳.۱ گفت‌وگو — `Verified` در baseline محلی

- گفت‌وگوی شخصی، گروهی و واحد سازمانی با عضویت شناسه‌محور.
- جست‌وجوی فرد با نام، نام کاربری، کد پرسنلی، واحد و سمت.
- متن، فایل، ویس، ضبط میکروفن و Drag & Drop با کنترل نوع و حجم.
- جست‌وجوی پیام/فرستنده/نام فایل و پنل فایل‌ها و ویس‌های مشترک.
- پاسخ، ویرایش و حذف زمان‌دار به‌صورت tombstone، شمارنده خوانده‌نشده و رسید خواندن.
- مالک و مدیر گروه، تغییر اعضا، پنهان‌کردن شخصی گفتگو و قطع دسترسی عضو حذف‌شده.

### ۳.۲ نامه‌نگاری — `Verified` در baseline محلی

- نامه داخلی/وارده/صادره، پیش‌نویس، بازبینی مستقل و ارسال نهایی.
- گیرنده فردی/واحدی، رونوشت، مهلت پاسخ، طبقه‌بندی و رسید مشاهده.
- رمز دوم چهاررقمی، قفل موقت، چاپ A4، شماره‌گذاری و مهر سیستمی SHA-256.
- بایگانی شخصی و اصلاحیه append-only بدون حذف تاریخچه دیگران.

### ۳.۳ وظیفه — `Implemented-Unverified` عمومی

- store `tasks` و ماژول عمومی `task` وجود دارد.
- وضعیت‌های `todo`، `in_progress`، `blocked`، `done` و `reopened`، سررسید، اولویت، مسئول و تاریخچه عمومی وجود دارند.
- فرم و سرویس فعلی generic است؛ هنوز قرارداد تخصصی پروژه، چک‌لیست، برچسب، ساخت چندمسئولی، داشبورد همکاری و آزمون کامل دامنه Task ندارد.

## ۴. شکاف واقعی؛ چه چیزی ساخته می‌شود

> **به‌روزرسانی پیاده‌سازی ۲۰۲۶/۰۸/۲۷:** موارد ۱ تا ۸ این بخش در شاخهٔ قابلیت اجرا شده‌اند: پروژه و عضویت صریح، داشبورد همکاری، Task تخصصی با checklist/label/reminder، ساخت اتمیک چندوظیفه‌ای، گفت‌وگوی اختیاری پروژه، نمایش نامه/سند پیوندخورده، pin/mute شخصی و فیلتر/رفتن به تاریخ در گفتگو. عبارت «واگذارشده به دیگران» به‌جای «منتظر دیگران» استفاده شده تا با دادهٔ واقعی اشتباه نشود. قابلیت‌های صرفاً سروری همچنان خارج از V1 هستند.

1. ظرف مستقل «پروژه» با مالک، اعضای صریح، وضعیت، بازه زمانی و نسخه.
2. داشبورد همکاری با پروژه‌های من، کارهای امروز، سررسیدگذشته، منتظر/مسدود و فعالیت اخیر.
3. صفحه پروژه با تب‌های نمای کلی، وظایف، گفت‌وگو، نامه‌ها و اسناد؛ تب‌ها همان منابع فعلی را فیلتر می‌کنند.
4. Task تخصصی شامل چک‌لیست، برچسب، سررسید، دلیل انتظار/انسداد و نماهای فهرست/برد.
5. ایجاد چند وظیفه مستقل برای چند مسئول، با شناسه دسته مشترک و تراکنش all-or-nothing.
6. گفت‌وگوی اختیاری پروژه با استفاده از Chat گروهی فعلی؛ نه مدل پیام تازه.
7. پیوند اختیاری منابع موجود با `payload.projectId` بدون تغییر معنای `relatedRecordId`.
8. تنظیم شخصی پین/بی‌صداکردن گفتگو در store جدا و بدون تغییر عضویت یا تاریخچه.

## ۵. مواردی که دوباره ساخته نمی‌شوند

- پیام، فایل، ویس، ضبط، رسید خواندن، ویرایش یا حذف پیام.
- شماره نامه، طبقه‌بندی، رمز دوم، امضا/مهر، چاپ و گردش نامه.
- store دوم برای «پیام پروژه» یا «نامه پروژه».
- واحد سازمانی موازی با پروژه.
- یک Task مشترک با چند مسئول که پاسخ‌گویی فردی را مبهم کند.
- projection دائمی برای شمارنده‌های داشبورد؛ Dashboard از منابع مرجع محاسبه می‌شود.

## ۶. قرارداد داده V1

### ۶.۱ Project

Project یک `OperationalRecord` تخصصی با `moduleId: 'project'` و store `projects` است.

| فیلد | قاعده |
|---|---|
| `id`, `trackingCode`, `companyId`, `version` | تولید سامانه؛ تغییرناپذیر یا versioned طبق Foundation |
| `title` | الزامی، trim‌شده، حداقل ۳ و حداکثر ۱۲۰ نویسه |
| `description` | اختیاری، حداکثر ۲۰۰۰ نویسه |
| `status` | `draft`، `active`، `paused`، `completed` یا `archived` |
| `ownerUserId` | کاربر فعال همان شرکت؛ همیشه در `memberUserIds` |
| `memberUserIds` | شناسه یکتای کاربران فعال همان شرکت؛ حداقل مالک |
| `unitId` | زمینه گزارش اختیاری؛ عضویت خودکار ایجاد نمی‌کند |
| `startAt`, `dueAt` | ISO/Gregorian در داده؛ نمایش شمسی با کنترل موجود |
| `chatConversationId` | شناسه Chat گروهی موجود؛ اختیاری و یکتا برای گفت‌وگوی اصلی پروژه |
| `payload` | فقط داده ساختاری پروژه؛ بدون متن نامه، فایل، رمز یا داده حساس تکراری |

### ۶.۲ Task تخصصی

Task در store فعلی `tasks` باقی می‌ماند. فیلدهای مشترک `OperationalRecord` حفظ و payload زیر افزوده می‌شود:

- `projectId?: string`؛ پروژه فعال و قابل مشاهده برای actor.
- `checklist: Array<{id, title, completed, completedAt?, completedByUserId?}>`.
- `labels: Array<{id, title, tone}>` با رنگ معنایی موجود و متن اجباری.
- `waitingReason?: string` برای وضعیت `blocked`.
- `assignmentBatchId?: string` برای وظایفی که از یک ثبت چندمسئولی ساخته شده‌اند.

هر Task دقیقاً یک `assigneeUserId` دارد. مسئول باید عضو فعال همان پروژه باشد. تکمیل همه اقلام چک‌لیست شرط رفتن به `done` است؛ Task بدون چک‌لیست می‌تواند طبق workflow فعلی تکمیل شود. تغییر وضعیت و checklist با `expectedVersion` انجام می‌شود.

### ۶.۳ پیوند منابع موجود

- Task، Chat، Letter و Document می‌توانند `payload.projectId` داشته باشند.
- `relatedRecordId` معنای فعلی خود را حفظ می‌کند؛ برای نمونه Message همچنان با آن به Chat متصل است.
- متن نامه، بدنه پیام، فایل و ویس در Project کپی یا index نمی‌شوند.
- جست‌وجوی پروژه فقط داده‌ای را برمی‌گرداند که actor هم عضو پروژه و هم مجاز به مشاهده منبع اصلی باشد.

### ۶.۴ Chat preference

store `chat_preferences` رکوردی با کلید پایدار کاربر+گفت‌وگو، `pinned`، `muted`، `updatedAt` و `version` نگه می‌دارد. Preference شخصی است و نباید در رکورد Chat، membership یا History اعضای دیگر نوشته شود.

## ۷. قواعد عضویت و دسترسی

### ۷.۱ اصل اشتراک دسترسی

نمایش یک منبع از مسیر هاب تنها وقتی مجاز است که همه شروط زیر برقرار باشند:

1. کاربر عضو صریح پروژه باشد؛
2. permission مؤثر عملیات را داشته باشد؛
3. Scope و Resource Policy منبع منطبق باشد؛
4. برای Chat عضو همان گفتگو باشد؛
5. برای Letter گیرنده/سازنده/بازبین مجاز باشد و قواعد طبقه‌بندی/رمز دوم رعایت شود.

عضویت پروژه هیچ مجوز منبعی تولید نمی‌کند. برعکس، دسترسی مستقل به یک نامه رسمی در کارتابل نامه طبق قواعد Letter حفظ می‌شود، اما تا وقتی کاربر عضو پروژه نیست از مسیر هاب و جزئیات پروژه نمایش داده نمی‌شود.

### ۷.۲ permissionهای پروژه و وظیفه

| عملیات | permission لازم | شرط منبع |
|---|---|---|
| دیدن فهرست/جزئیات پروژه | `task.project.view` | عضویت صریح همان پروژه |
| ساخت پروژه | `task.project.create` | actor فعال در همان شرکت؛ مالک خود actor یا کاربر مجاز صریح |
| ویرایش مشخصات | `task.project.edit` | مالک یا مدیر پروژه مجاز |
| مدیریت اعضا/مالکیت/آرشیو | `task.project.manage` | مالک یا مدیر پروژه؛ `expectedVersion` الزامی |
| دیدن Task پروژه | `task.task.view` | عضویت پروژه + سیاست فعلی Task |
| ساخت Task | `task.task.create` | عضویت پروژه؛ مسئول فقط از اعضای فعال |
| ویرایش Task | `task.task.edit` | سازنده/مالک پروژه/مدیر مجاز یا مسئول در فیلدهای مجاز خودش |
| تغییر وضعیت | `task.task.transition` | مسئول همان Task یا مدیر مجاز + transition جاری |
| مدیریت کلی Task | `task.task.manage` | عضویت پروژه + Scope/Resource Policy |

denial فردی همچنان بر grant و نقش برنده است. نام نقش، عنوان شغلی یا مخفی‌کردن دکمه در UI جای enforce سرویس را نمی‌گیرد.

### ۷.۳ حذف عضو

- حذف عضو با command نسخه‌دار انجام می‌شود و دسترسی او به پروژه فوراً قطع می‌شود.
- اگر گفت‌وگوی اصلی پروژه وجود دارد، همان کاربر در همان transaction از اعضای آن Chat نیز حذف می‌شود.
- رکورد، History، Audit، پیام یا نامه او حذف فیزیکی نمی‌شود.
- منابع مستقل مانند نامه‌ای که قبلاً رسماً به او ارسال شده است در ماژول اصلی خود تابع retention و قواعد همان دامنه می‌ماند؛ حذف عضویت پروژه سابقه رسمی را پاک نمی‌کند.
- Task فعالِ مسئول حذف‌شده باید در UI مالک پروژه به‌عنوان «نیازمند تعیین تکلیف» دیده شود و actor حذف‌شده حق اقدام بعدی ندارد.

## ۸. تجربه کاربری و ناوبری

### ۸.۱ داشبورد همکاری

- کارت «پروژه‌های من» با وضعیت و پیشرفت حاصل از Taskهای قابل مشاهده.
- صف «امروز» برای سررسید روز جاری، «عقب‌افتاده» برای سررسید گذشته و ناتمام، و «منتظر» برای `blocked`.
- فعالیت اخیر از History قابل مشاهده همان پروژه‌ها؛ بدون نمایش متن نامه محرمانه یا داده فایل.
- اقدام سریع: ساخت پروژه، ساخت وظیفه و ورود به گفت‌وگوی پروژه، فقط در صورت داشتن مجوز.
- شمارنده‌ها در زمان خواندن محاسبه می‌شوند و با reload از داده مرجع یکسان می‌مانند.

### ۸.۲ صفحه پروژه

- سربرگ: عنوان، وضعیت، مالک، اعضا، تاریخ‌ها و درصد پیشرفت.
- «نمای کلی»: خلاصه صف‌ها و آخرین فعالیت مجاز.
- «وظایف»: فهرست و برد وضعیت با فیلتر مسئول، برچسب، سررسید و وضعیت.
- «گفت‌وگو»: بازکردن Chat گروهی فعلی؛ اگر وجود ندارد فقط actor مجاز می‌تواند آن را اتمیک بسازد.
- «نامه‌ها»: فقط فهرست نامه‌های پیوندخورده‌ای که کاربر طبق Letter مجاز به دیدن آن‌هاست؛ عنوان نامه قفل‌شده یا متن آن به عضو غیرمجاز نشت نمی‌کند.
- «اسناد»: فقط metadata سند مجاز؛ فایل از مسیر تخصصی خودش باز می‌شود.

همه نماها RTL، responsive و keyboard-accessible هستند؛ modal، validation، PersianDate، empty/loading/error state و tab workspace از الگوهای فعال پروژه استفاده می‌کنند.

## ۹. دامنه فازها

### فاز ۱ — بنیاد پروژه و دسترسی

- module/store پروژه، permission catalog، نقش‌های پایه و migration 11→12.
- CRUD نسخه‌دار پروژه، عضویت صریح و قطع دسترسی عضو حذف‌شده.
- ایجاد اتمیک پروژه با Chat گروهی اختیاری.
- فهرست «پروژه‌های من» و صفحه نمای کلی پایه.
- تست سرویس، denied path، تراکنش و مهاجرت قبل از UI کامل.

**خروج فاز:** پروژه‌ای که actor عضو آن نیست در state، search، شمارنده و URL مستقیم قابل کشف نیست.

### فاز ۲ — Task تخصصی و داشبورد

- commandهای تخصصی ساخت/ویرایش/transition/checklist.
- ساخت چندمسئولی به شکل Taskهای مستقل اتمیک.
- لیست/برد، امروز، عقب‌افتاده، منتظر و پیشرفت پروژه.
- notification محلی برای عضویت و انتساب؛ بدون ادعای Push.
- reload، concurrency و accessibility tests.

**خروج فاز:** هر مسئول فقط رکورد خودش را پیش می‌برد و جمع داشبورد از source of truth قابل بازتولید است.

### فاز ۳ — اتصال منابع و سخت‌سازی محلی

- پیوند پروژه به Chat/Letter/Document موجود بدون store موازی.
- پین/بی‌صداکردن شخصی گفتگو با `chat_preferences`.
- جست‌وجوی پروژه و فعالیت اخیر با redaction و visibility intersection.
- snapshot 12، ارتقای snapshot 11، failure injection و E2E کامل RTL/mobile/axe.
- بازبینی مستقل امنیت، محصول، UI و داده.

**خروج فاز:** همه معیارهای پذیرش V1 پاس شده‌اند و قابلیت فقط به‌عنوان «پایلوت محلی کنترل‌شده» گزارش می‌شود.

## ۱۰. مهاجرت و پایداری داده

1. `FOUNDATION_SCHEMA_VERSION` از ۱۱ به ۱۲ افزایش می‌یابد.
2. storeهای `projects` و `chat_preferences` به‌صورت additive ساخته می‌شوند؛ هیچ store یا رکورد نسخه ۱۱ پاک/clear نمی‌شود.
3. Task، Chat، Letter و Document قدیمی بدون `projectId` معتبر می‌مانند و در یک پروژه ساختگی قرار نمی‌گیرند.
4. seed فقط رکوردهای seed-owned گمشده را idempotent اضافه می‌کند و پروژه/عضویت/تغییر کاربر را overwrite نمی‌کند.
5. snapshot نسخه ۱۲ هر دو store جدید را صادر می‌کند؛ import نسخه ۱۱ از مسیر upgrader صریح آرایه خالی برای آن‌ها می‌سازد و سپس checksum/shape را مطابق قرارداد ارتقا اعتبارسنجی می‌کند.
6. آزمون migration باید از fixture واقعی ساختار نسخه ۱۱ ساخته شود، نه از seed نسخه ۱۲ با حذف دستی فیلدها.
7. هر عملیات چندstore شامل Project/Task/Chat/History/Audit/Event/Notification در یک IndexedDB transaction است؛ خطای میانی rollback کامل دارد.

## ۱۱. معیارهای پذیرش V1

### پروژه و عضویت

- **AC-P01:** کاربر دارای مجوز پروژه می‌سازد و پس از reload همان نسخه و اعضا را می‌بیند.
- **AC-P02:** کاربر غیرعضو پروژه را در فهرست، جست‌وجو، شمارنده، URL مستقیم و state دریافت نمی‌کند.
- **AC-P03:** مالک همیشه عضو است؛ حذف یا تکرار مالک در ورودی رد می‌شود.
- **AC-P04:** عضو حذف‌شده در همان transaction دسترسی پروژه و Chat اصلی پروژه را از دست می‌دهد؛ History/Audit باقی می‌ماند.
- **AC-P05:** رقابت دو ویرایش با `expectedVersion` قدیمی fail می‌شود و داده آخرین نسخه سالم می‌ماند.

### وظیفه

- **AC-T01:** فقط عضو فعال پروژه می‌تواند مسئول Task باشد.
- **AC-T02:** انتخاب سه مسئول دقیقاً سه Task مستقل با یک `assignmentBatchId` می‌سازد؛ شکست رکورد دوم هیچ‌یک را ذخیره نمی‌کند.
- **AC-T03:** مسئول فقط Task خودش را در transition مجاز پیش می‌برد؛ عضو دیگر و QA با denied path رد می‌شوند.
- **AC-T04:** Task دارای checklist ناقص به `done` نمی‌رود و اولین نقص در فرم focus/نمایش داده می‌شود.
- **AC-T05:** امروز، عقب‌افتاده و منتظر با تاریخ ISO و نمایش شمسی، مرز نیمه‌شب و وضعیت نهایی را درست محاسبه می‌کنند.
- **AC-T06:** حذف عضو، Task فعال او را برای مالک «نیازمند تعیین تکلیف» می‌کند و actor حذف‌شده نمی‌تواند آن را تغییر دهد.

### استفاده مجدد و محرمانگی

- **AC-V01:** پروژه+Chat اختیاری یا هر دو ساخته می‌شوند یا هیچ‌کدام؛ Chat از سرویس و store موجود استفاده می‌کند.
- **AC-V02:** عضو پروژه‌ای که عضو Chat پیوندخورده نیست، پیام یا نام فایل آن را نمی‌بیند.
- **AC-V03:** عضو پروژه بدون مجوز Letter، نامه پیوندخورده، موضوع محافظت‌شده، متن، گیرندگان و شمارنده افشاگر دریافت نمی‌کند.
- **AC-V04:** گیرنده رسمی نامه پس از حذف از پروژه، نامه را فقط طبق سیاست Letter در کارتابل رسمی خود حفظ می‌کند و از هاب پروژه کنار گذاشته می‌شود.
- **AC-V05:** پروژه هیچ کپی از متن پیام، متن نامه، data URL فایل، رمز دوم، OTP یا داده بانکی نگه نمی‌دارد.

### UX، پایداری و مرز محلی

- **AC-U01:** همه عملیات اصلی با صفحه‌کلید، focus قابل مشاهده و نام دسترس‌پذیر انجام می‌شوند؛ axe blocker ندارد.
- **AC-U02:** لیست، برد و جزئیات در RTL، عرض موبایل و تم روز/شب بدون overflow مخرب کار می‌کنند.
- **AC-U03:** reload و بازکردن تب کاری دیگر داده فرم ذخیره‌شده را از بین نمی‌برد؛ فرم dirty طبق guard فعلی بسته نمی‌شود.
- **AC-U04:** پین/بی‌صداکردن فقط preference همان کاربر را تغییر می‌دهد و عضو دیگر تفاوتی نمی‌بیند.
- **AC-U05:** UI عبارت روشنی درباره «ذخیره محلی همین مرورگر» دارد و هیچ نشان حضور آنلاین یا تحویل realtime جعلی نمایش نمی‌دهد.
- **AC-M01:** ارتقای دیتابیس و snapshot 11→12 داده، شناسه، نسخه و History قبلی را حفظ می‌کند و اجرای دوباره idempotent است.

## ۱۲. برنامه آزمون و دروازه خروج

| سطح | آزمون الزامی |
|---|---|
| واحد/دامنه | validation Project/Task، selectorهای Dashboard، تاریخ/برچسب/checklist و redaction |
| مجوز منفی | غیرعضو، Scope نامنطبق، denial فردی، عضو پروژه بدون Chat/Letter access، QA بدون bypass |
| تراکنش | failure injection در create Project+Chat، ساخت چند Task و حذف عضو+Chat |
| هم‌زمانی | expectedVersion قدیمی برای پروژه، اعضا، checklist و preference |
| migration | fixture واقعی schema 11، upgrade دیتابیس، import snapshot 11، export/import 12 و اجرای مجدد |
| persistence | reload برای پروژه، Task، preference، history و notification |
| مرورگر | سناریوی مالک/عضو/غیرعضو، لیست/برد، فیلترها، پیوند Chat/Letter/Document |
| UI | RTL، موبایل، روز/شب، keyboard، focus، modal guard و axe |
| Gate مخزن | `npm run typecheck`، `npm test`، `npm run build` و E2Eهای ریسک‌محور طبق policy |

قابلیت فقط وقتی از `In progress` به `Verified` می‌رود که همه ACهای همان فاز، آزمون‌های منفی و Gateهای لازم پاس باشند و بازبینی مستقل Finding حل‌نشده نداشته باشد.

## ۱۳. خارج از V1 و نیازمند مرحله Server

- تحویل بلادرنگ، presence/typing، retry شبکه و همگام‌سازی چنددستگاهی.
- اعلان Push/SMS واقعی و OTP سروری.
- object storage، antivirus، URL کوتاه‌عمر و quota سازمانی فایل.
- ویدئوکنفرانس/تماس آنلاین و WebRTC سازمانی.
- retention حقوقی مرکزی، eDiscovery، قفل نگهداری و Audit tamper-evident سروری.
- تقویم اشتراکی سروری، recurrence پیچیده و اتصال بیرونی.
- UAT چندکاربر هم‌زمان و SLA بهره‌برداری.

این موارد ممکن است پس از V1 به محصول اضافه شوند، اما نبودشان نباید با داده نمایشی یا status غیرواقعی پوشانده شود.

## ۱۴. تصمیم‌های باز آینده

هیچ‌یک از موارد زیر مانع اجرای V1 محلی نیست، اما پیش از Server باید ADR جدا داشته باشد:

1. سیاست اضطراری دسترسی پشتیبانی به پروژه خصوصی و نحوه تأیید/گزارش آن.
2. retention حقوقی پیام، فایل، پروژه آرشیوی و عضو حذف‌شده.
3. مدل notification، presence و conflict resolution چنددستگاهی.
4. محل object storage، اسکن بدافزار و کلیدهای رمزگذاری.
5. سطح رسمی تقویم، جلسه، رأی‌گیری، منشن و تماس تصویری در نسخه‌های بعد.
