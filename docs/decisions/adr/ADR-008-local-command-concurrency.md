# ADR-008 — Local Command Concurrency and Browser-Profile Session

> Status: ACCEPTED
> Date: 2026-08-28

## Context

نسخه جاری شاهراه یک برنامه local-first بر پایه IndexedDB است. چند تب یک browser profile پایگاه و نشست مشترک دارند؛ بنابراین بررسی نسخه، نقش یا هویت فقط پیش از شروع فرمان می‌تواند به ثبت با نشست قدیمی، دوباره‌کاری یا باقی‌ماندن نیمی از handoff منجر شود.

## Decision

- هر browser profile فقط یک هویت فعال مشترک دارد. تغییر ورود، خروج یا مشاهده آزمایشی نشست را versioned می‌کند و به تب‌های دیگر پیام invalidation می‌فرستد؛ تب قدیمی اجازه ثبت فرمان ندارد.
- mutation عمومی رکورد عملیاتی در همان `readwrite transaction`، نشست، کاربر فعال، نقش‌های جاری، مجوز، محدوده، نسخه رکورد و مسیر pinned گردش‌کار را دوباره بررسی می‌کند.
- CAS بر نسخه رکورد اعمال می‌شود. فرمان با نسخه قدیمی بدون هیچ write رد می‌شود.
- شماره پیگیری هنگام transaction و از آخرین داده همان store تخصیص داده می‌شود، نه از snapshot قبلی UI.
- receipt فرمان شامل `commandId`، اثرانگشت نسخه‌دار `SHA-256` درخواست و نتیجه است. اثرانگشت پیش از بازشدن تراکنش IndexedDB محاسبه می‌شود تا هیچ `await` رمزنگاری عمر تراکنش را قطع نکند. تکرار همان شناسه و همان payload همان نتیجه را برمی‌گرداند؛ استفاده همان شناسه با payload دیگر fail-closed است.
- تغییر منبع، history، audit، event، receipt، meta و رکورد مقصد handoff یک outcome اتمیک هستند. شکست هر write کل outcome را rollback می‌کند.
- مقصد handoff به نسخه منتشرشده، وضعیت آغاز و مسیر همان نسخه pin می‌شود؛ تغییر بعدی سیاست، پرونده ساخته‌شده را بی‌مرجع نمی‌کند.
- ماژول دارای API تخصصی با `mutationMode: specialized` از create/update/transition/assign عمومی عبور نمی‌کند. حالت مشاهده آزمایشی مدیر نیز برای همه mutationهای عمومی فقط‌خواندنی است.
- ورود گروهی مشتریان یک فرمان اتمیک است: ردیف‌ها با snapshot جاری همان شرکت نرمال‌سازی و از نظر تکراری بودن بررسی می‌شوند و مشتریان، گزارش ورود، ممیزی، رویداد دامنه و receipt همگی در یک تراکنش ثبت یا همگی rollback می‌شوند.
- پیگیری خزانه به نسخه و وضعیت جاری درخواست خرید و صف‌های خزانه متصل است. گیرندگان از کاربران، نقش‌ها، مجوز و محدوده جاری داخل همان تراکنش محاسبه می‌شوند و اعلان، history، audit، رویداد و receipt یک outcome هستند. محدودیت یک پیگیری در روز از receipt فرمان جدا است تا retry همان فرمان به خطای تکراری روزانه تبدیل نشود.
- projection صف تغییرات پرسنل و رخدادهای CRM با resource واقعی هدف و scope همان entitlement فیلتر می‌شود؛ metadata ناقص یا شناسه خارج از محدوده fail-closed است.
- همه mutationهای احرازشده خانواده جذب (ثبت مستقیم منابع انسانی، ویرایش پرونده متقاضی، استفاده مجدد بانک استعداد و شروع دوره آموزشی) نشست، نقش، رکورد و واحد/شعبه مقصد را داخل همان transaction بازاعتبارسنجی می‌کنند. مالکیت tenant واحدهای legacy فقط با یک شرکت یکتای قابل استنتاج پذیرفته می‌شود؛ سمت باید به واحد همان شرکت متصل باشد. فرم عمومی متقاضی عمداً بدون نشست باقی می‌ماند، اما tenant مقصد را از واحد معتبر استنتاج می‌کند و هرگز از شناسه شرکت hard-coded استفاده نمی‌کند.

## Consequences

- دوبارکلیک، retry و رقابت چند تب رکورد یا history تکراری تولید نمی‌کند.
- تغییر هویت یا لغو نقش میان آماده‌سازی UI و commit، فرمان را متوقف می‌کند.
- تب قدیمی باید تازه‌سازی شود؛ هویت مستقل برای هر تب پشتیبانی نمی‌شود.
- baseline مرورگر این تصمیم، یک browser profile با IndexedDB و Web Crypto (`crypto.subtle`) در secure context مانند `https` یا `localhost` است. تست‌های fake-indexeddb رقابت تب‌های همان پایگاه را می‌سنجند؛ ناسازگاری مرورگرهای بدون Web Crypto در این baseline پشتیبانی نمی‌شود.
- این تصمیم ایمنی داخل یک IndexedDB مشترک را پوشش می‌دهد و ادعای ظرفیت چند دستگاه یا صدهاهزار کاربر نیست. آن سطح به backend تراکنشی و آزمون بار سرور نیاز دارد.

## Deferred decisions

- مسیرهای تخصصی باقی‌مانده‌ای که هنوز receipt نسخه‌دار ندارند باید در بسته تخصصی خود همگرا شوند؛ وجود CAS یا تراکنش در یک مسیر به‌تنهایی جای قرارداد retry را نمی‌گیرد.
- ثبت تخصصی مساعده و درخواست خرید اکنون snapshot نشست، منع مشاهده آزمایشی مدیر، بازاعتبارسنجی نقش/مجوز داخل تراکنش و receipt نسخه‌دار SHA-256 دارد؛ retry همان فرمان همان نتیجه را برمی‌گرداند و payload متفاوت رد می‌شود. طراحی موتور approval/continuity و قواعد چندتأییدی همچنان تصمیم جداگانه فاز بعد است.
- برای backend آینده، unique constraint شماره‌ها، transaction پایگاه سرور، outbox و کلید idempotency سمت سرور الزامی است.
