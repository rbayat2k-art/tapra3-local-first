## قانون تغییر تصمیم

`Documented` — تصمیم تصویب‌شده حذف یا بی‌صدا بازنویسی نمی‌شود. تاریخ، علت، اثر migration و تصمیم جایگزین به همین سند افزوده می‌شود. تصمیمی که کد آن را نقض می‌کند با `Conflict` علامت می‌خورد.

## ADRهای تفصیلی فعال

### ADR-A — Runtime مرورگرمحور و مرز ذخیره‌سازی

- **زمینه:** مالک محصول برای طراحی و پذیرش سریع به اجرای مستقل از Server نیاز دارد.
- **تصمیم:** UI فقط `LocalFoundationService` را می‌شناسد؛ سرویس فقط `StorageAdapter` را می‌شناسد؛ اجرای فعلی `IndexedDBAdapter` است.
- **گزینه‌های ردشده:** PostgreSQL/Express در این فاز؛ localStorage به‌عنوان دیتابیس عملیاتی.
- **پیامد مثبت:** اجرای آفلاین و تست سریع؛ امکان جایگزینی Adapter.
- **پیامد منفی:** دستگاه/profile نقطه شکست یکتا و کنترل امنیتی سمت سرور غایب است.
- **Migration:** `ServerApiAdapter` باید semantics و error contract سرویس محلی را حفظ کند.
- **شاهد:** `FoundationApp.tsx`, `service.ts`, `storage.ts`.

### ADR-B — مجوز مؤثر چندلایه

- **زمینه:** نام نقش به‌تنهایی برای تفکیک شرکت، واحد، تیم، خود و رکورد کافی نیست.
- **تصمیم:** Role permissions + per-user grants/denials + Scope + Resource Policy + Workflow Guard. Deny فردی برنده است.
- **گزینه‌های ردشده:** شرط‌های پراکنده در component؛ bypass برای QA persona.
- **پیامد:** تصمیم‌ها explainable و قابل Audit هستند؛ نگه‌داری ماتریس مجوز ضروری است.
- **امنیت:** QA login actor ادمین و effective user را جدا نگه می‌دارد.
- **شاهد:** `seed.ts`, `authorization.ts`, `organizationAccess.ts` و تست‌ها.

### ADR-C — Workflow نسخه‌دار با State Machine محافظت‌شده

- **زمینه:** مسیرها باید قابل تغییر باشند، اما تغییر آزاد stateها پرونده‌های جاری را خراب می‌کند.
- **تصمیم:** ترتیب stage، role، scope، تصمیم و route شعبه‌ای قابل نسخه‌گذاری است؛ state/transition مصوب آزادانه ویرایش نمی‌شود.
- **پیامد:** نسخه و route هنگام ایجاد روی رکورد freeze می‌شود. تغییر سیاست فقط رکورد جدید را می‌گیرد.
- **محدودیت:** quorum، escalation زمانی و expressionهای شرطی `Planned` هستند.
- **شاهد:** `workflowPolicy.ts`, `WorkflowAdminPage.tsx`, `service.updateWorkflowPolicy`.

### ADR-D — Audit، History و Domain Event در همان Transaction

- **زمینه:** تصمیم، actor، زمان، reason و handoff باید قابل پیگیری بمانند.
- **تصمیم:** تغییر عملیاتی همراه history، audit، domain event و meta در یک transaction IndexedDB نوشته می‌شود.
- **پیامد:** failure میانی rollback می‌شود؛ اما tamper evidence مستقل از دستگاه وجود ندارد.
- **مهاجرت آینده:** outbox یا event log سمت سرور باید correlation و ordering را حفظ کند.
- **شاهد:** `persistOperationalChange` و `StorageAdapter.transaction`.

### ADR-E — هاب همکاری پروژه‌محور، مرزهای دسترسی و اجرای Local-first

- **شناسه مرجع:** `ADR-016`.
- **وضعیت:** `Accepted / Verified (Local-first)`؛ معیارهای V1 محلی، آزمون کامل و بازبینی‌های مستقل در ۲۰۲۶/۰۸/۲۷ پاس شدند. قابلیت‌های سروری همچنان خارج از این تصمیم‌اند.
- **تاریخ:** ۲۰۲۶/۰۸/۲۷.
- **زمینه:** شاهراه اکنون گفت‌وگوی شخصی/گروهی/واحدی، نامه‌نگاری تخصصی و یک ماژول عمومی `task` دارد. شکاف واقعی، ظرف پروژه، نمای روزانه همکاری و رفتار تخصصی وظیفه است. ساخت دوباره پیام، نامه یا فایل در یک مدل «همکاری» جدید، دو مرجع حقیقت و دو سیاست دسترسی ناسازگار ایجاد می‌کند.
- **تصمیم — Project Hub:** یک ماژول عملیاتی `project` با store مستقل `projects` به Registry افزوده می‌شود. پروژه فقط برای اعضای صریح همان پروژه قابل مشاهده است؛ مالک پروژه همیشه عضو است. عضویت با شناسه پایدار کاربر ذخیره می‌شود، نه نام نمایشی، واحد یا سمت. حذف عضو، دسترسی آینده او به خود پروژه را همان لحظه قطع می‌کند و سابقه Audit/History را حذف نمی‌کند.
- **تصمیم — تخصصی‌سازی Task:** رکوردهای وظیفه در store فعلی `tasks` و workflow فعلی باقی می‌مانند، اما commandها و UI تخصصی پروژه، سررسید، چک‌لیست، برچسب، دلیل انتظار/انسداد و نماهای «امروز»، «گذشته از سررسید» و «منتظر» را اضافه می‌کنند. انتخاب چند مسئول، یک رکورد مشترک چندمالک نمی‌سازد؛ برای هر مسئول یک وظیفه مستقل و قابل حسابرسی در یک تراکنش ساخته می‌شود و `assignmentBatchId` آن‌ها را به هم مرتبط می‌کند.
- **تصمیم — پیوند صریح:** `payload.projectId` پیوند اختیاری و یکسان روی Task، Chat، Letter و Document است. `relatedRecordId` برای معنای فعلی هر ماژول حفظ می‌شود و به شناسه پروژه تغییر معنا نمی‌دهد.
- **تصمیم — عدم تکرار:** گفت‌وگوی پروژه همان رکورد موجود `chat` از نوع `group` است و نامه پروژه همان رکورد موجود `letter` است. هاب فقط میان‌بُر، فیلتر و پیوند ایجاد می‌کند؛ پیام، پیوست، رسید خواندن، سطح محرمانگی، رمز دوم، شماره نامه، امضا، چاپ و تاریخچه در سرویس‌های تخصصی فعلی باقی می‌مانند. ایجاد پروژه همراه با گفت‌وگوی اختیاری باید اتمیک باشد.
- **تصمیم — اشتراک دسترسی (visibility intersection):** برای نمایش هر منبع پیوندخورده از مسیر هاب، عضویت پروژه شرط لازم است، نه مجوز جایگزین. نمایش نیازمند اشتراک همه محدودیت‌هاست: عضویت پروژه **و** مجوز/Scope منبع **و** Resource Policy **و** قواعد عضویت Chat یا گیرندگی/طبقه‌بندی Letter. عضویت پروژه هرگز نامه محرمانه یا گفت‌وگویی را که کاربر عضو آن نیست آشکار نمی‌کند؛ دسترسی ادمین و QA نیز این قواعد را دور نمی‌زند. دسترسی رسمی مستقلی که خود دامنه Letter برای گیرنده ثبت کرده است در کارتابل نامه تابع retention همان دامنه می‌ماند و با حذف عضویت پروژه پاک نمی‌شود.
- **تصمیم — Dashboard مشتق‌شده:** نمای همکاری از `projects`، `tasks` و منابع پیوندخورده در زمان خواندن محاسبه می‌شود. در این مرحله projection یا store جدیدی برای شمارنده‌های Dashboard ساخته نمی‌شود؛ داده مشتق‌شده نباید مرجع حقیقت دوم شود.
- **تصمیم — Preference گفتگو:** پین/بی‌صداکردن و تنظیمات شخصی گفت‌وگو در store مستقل `chat_preferences` و با کلید کاربر+گفت‌وگو نگهداری می‌شود؛ این ترجیحات عضویت، تاریخچه یا رکورد گفت‌وگو را تغییر نمی‌دهند.
- **مرز Local-first:** اجرای این ADR فقط در یک پروفایل مرورگر و IndexedDB معتبر است. «همکاری» در این نسخه به معنی همگام‌سازی زنده، حضور آنلاین، تحویل چنددستگاهی، Push، فایل مرکزی، قفل توزیع‌شده یا امنیت تولیدی نیست. این موارد تا Server/API مرکزی `Planned` می‌مانند و UI نباید خلاف آن را القا کند.
- **مهاجرت:** نسخه schema از ۱۱ به ۱۲ فقط با افزودن `projects` و `chat_preferences` بالا می‌رود. ارتقا باید additive و idempotent باشد، storeهای نسخه ۱۱ و شناسه/تاریخچه موجود را حفظ کند، snapshot نسخه ۱۱ را با مسیر ارتقای صریح بپذیرد و snapshot نسخه ۱۲ را کامل صادر کند. reset یا بازسازی داده کاربر راه مهاجرت نیست.
- **اتمی‌بودن:** ایجاد پروژه+گفت‌وگوی اختیاری، ایجاد دسته وظایف چندمسئولی، تغییر اعضا همراه History/Audit/Event، و پیوند/قطع پیوند منبع باید هرکدام در یک transaction باشند. شکست میانی نباید پروژه بدون گفت‌وگوی وعده‌داده‌شده یا دسته وظیفه ناقص برجای بگذارد.
- **گزینه‌های ردشده:** ساخت مجموعه `project_messages`/`project_letters`؛ استفاده از واحد سازمانی به‌عنوان پروژه؛ چندمسئولی‌کردن یک Task؛ اعطای دسترسی منابع فقط به دلیل عضویت پروژه؛ ذخیره شمارنده‌های Dashboard به‌عنوان داده عملیاتی.
- **پیامد مثبت:** تجربه همکاری یکپارچه می‌شود، در حالی که امنیت و تاریخچه Chat/Letter یک مرجع می‌ماند و Task قابل گزارش و پاسخ‌گویی فردی است.
- **پیامد منفی:** کنترل دسترسی هر نمایش و command باید چند منبع را هم‌زمان ارزیابی کند؛ مهاجرت snapshot پیچیده‌تر می‌شود؛ تجربه بلادرنگ تا مرحله سرور محدود می‌ماند.
- **شاهد فعلی:** `communications.ts`، `CommunicationsPage.tsx`، `letters.ts`، `LettersPage.tsx`، ماژول عمومی `task` در `erpCatalog.ts` و storeهای `tasks`/`chats`/`messages`/`letters` در `model.ts`.
- **معیار بازنگری:** هنگام طراحی Server/API، ADR جدید باید مدل همگام‌سازی، authorizer سمت سرور، object storage، حضور/اعلان بلادرنگ و مهاجرت شناسه‌ها را تعیین کند؛ این ADR بدون ثبت تصمیم جایگزین حذف نمی‌شود.

## ADRهای تاریخی

فایل‌های `docs/decisions/adr/ADR-001` تا `ADR-007` طراحی Server/PostgreSQL قدیمی‌اند. آن‌ها برای بازیابی دانش حفظ شده‌اند، اما برای runtime جاری `Deprecated` هستند و شناسه‌هایشان با جدول تصمیم‌های Local-first بالا یک namespace مشترک ندارند.
