# ماتریس نقش، مجوز، محدوده و سیاست منبع

> **وضعیت:** `Verified` در commit پایه `853dac0` و تغییرات محلی ۱۴۰۵/۰۵/۳۱. منبع اصلی: `seed.ts`، `erpCatalog.ts`، `organizationAccess.ts`، `authorization.ts` و `workflowPolicy.ts`.

## مدل تصمیم دسترسی

تصمیم نهایی به‌ترتیب زیر محاسبه می‌شود:

1. حساب باید فعال باشد.
2. نقش‌های فعال کاربر جمع می‌شوند.
3. `permissionDenials` از مجوزهای نقش کم می‌شود؛ محرومیت صریح همیشه برنده است.
4. `permissionGrants` فردی اضافه می‌شود.
5. محدوده `COMPANY | UNIT | TEAM | SELF | RECORD` روی منبع بررسی می‌شود.
6. سیاست منبع، از جمله maker/checker، بررسی می‌شود.
7. انتقال وضعیت باید در ماشین وضعیت و تصمیم مرحله جاری مجاز باشد.

`Verified` — ادمین از `ADMIN_OPERATIONAL_PERMISSIONS` استفاده می‌کند، اما عملیات تجاری حساس همچنان از Guard و قواعد دامنه عبور می‌کنند. ورود آزمایشی نیز هویت ادمین واقعی و کاربر مؤثر را جداگانه در Audit نگه می‌دارد.

## محدوده‌ها

| محدوده | منبع مجاز | محدودیت |
|---|---|---|
| `COMPANY` | همه رکوردهای شرکت جاری | عبور از مرز شرکت ممنوع است. |
| `UNIT` | رکوردهای واحد کاربر | `unitId` باید برابر باشد. |
| `TEAM` | رکوردهای تیم کاربر | `teamId` باید برابر باشد. |
| `SELF` | رکورد ساخته‌شده یا متعلق به خود | مالک/سازنده با `actorId` تطبیق می‌شود. |
| `RECORD` | رکورد صریحاً واگذارشده | actor باید در فهرست مجاز رکورد باشد. |

## نقش‌های Registry عمومی

`Implemented-Unverified` — نقش‌های CRM، فروش، بازاریابی، تدارکات، تأمین‌کننده، مالی، حسابداری، انبار، لجستیک، خدمات، پشتیبانی، قرارداد، دارایی، وظایف، ارتباطات و اسناد در `ERP_ROLE_TEMPLATES` تعریف شده‌اند. مجوز هر نقش از ترکیب `domain.resource.action` ساخته می‌شود. عمق فرایندی این نقش‌ها، به‌جز سه گردش بالا، عمدتاً از Workspace عمومی استفاده می‌کند و E2E مستقل ندارد.

## شکاف‌ها

- `Unknown` — سیاست Production برای MFA، session timeout، lockout و password complexity تصویب نشده است.
- `Implemented-Unverified` — همه نقش‌های عمومی ERP آزمون رفتاری مستقل ندارند.
- `Planned` — اعمال authorization در سمت Server پس از جایگزینی Adapter؛ مدل UI نباید تغییر کند.
- `Unknown` — بازبینی دوره‌ای دسترسی‌ها، مالک approval و فرآیند recertification تعیین نشده است.

## سناریوی آزمون دستی حداقلی

1. با ادمین، یک کاربر فعال را با «ورود آزمایشی» باز کنید.
2. تطبیق دهید منو فقط از مجوزهای مؤثر ساخته شده است.
3. یک `permissionDenial` روی قابلیت قابل مشاهده اعمال و ناپدیدشدن منو/عمل را بررسی کنید.
4. همان مجوز را Grant کنید؛ چون Deny برنده است، دسترسی نباید برگردد.
5. یک رکورد خارج از Scope باز کنید؛ Guard باید دلیل فارسی `scope.denied` بدهد.
6. در پایان QA login، Audit باید actor ادمین و effective user را جدا نشان دهد.
